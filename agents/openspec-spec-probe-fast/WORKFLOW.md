# Fast 8.3-fast.3: формат и команды

Схема 8.0 расширена необязательными полями; старые отчёты читаются. Обновляйте весь Fast-пакет вместе. Новые отчёты используют parts. Оригинальный Probe не изменяется.

## Структура данных

Создайте <run>/_meta/parts/base.json: все обязательные поля report.schema.json, кроме findings и coverage; evidence_registry и вычисляемый verdict сюда не включайте. Создайте по одному JSON-объекту на файл для каждой находки, строки покрытия и доказательства. Все пути manifest относительны его каталогу; чтение вне него запрещено. Не включённые в manifest файлы не попадают в отчёт. Перед публикацией обязательно сверьте manifest с полным перечнем условий, OBS и находок; скрипт не может обнаружить забытое требование.

Пример manifest.json:
```json
{"base":"base.json","findings":["findings/F-01.json"],"coverage":["coverage/C-01.json"],"evidence_registry":["evidence/E-01.json"]}
```
Пустой список допустим, если соответствует реальному результату. Каждый файл записи содержит объект, не массив.

Пример evidence/E-01.json (образец формы, не готовое доказательство):
```json
{"id":"E-01","source":"src/auth.ts","location":"40–58, ревизия <SHA>","fact":"Повтор запроса вызывается только после успешного обновления токена.","method":"статический анализ"}
```
Добавляйте evidence_ids в findings и coverage. Обязательное findings.evidence остаётся массивом кратких оснований, coverage.basis — объяснением конкретного условия. Не копируйте туда полный факт/путь из реестра. Все ID обязаны существовать, дубли запрещены. Источники реестра описываются относительно итогового отчёта, а не каталога parts. Только реально проверенные факты и источники; выполненные команды отделяются от прочитанных тестов.

Для OBS вне выбранных сабтасков допускается in_scope=false только при kind=observation, status=unchecked и пустом finding_ids. Объяснение исключения обязательно в basis. Это не исключает OBS из покрытия и не скрывает наблюдения, влияющие на выбранную область. Для всех остальных записей in_scope отсутствует или true.

## Команды

Вместо SCRIPT используйте полный путь к установленному scripts/workflow.py; вместо REPORT — scripts/report.py. RUN и REPO — реальные абсолютные пути. shell-примеры ниже требуют подстановки значений.

```sh
python3 SCRIPT mark RUN code start
python3 SCRIPT mark RUN code end
# freeze выполняется до чтения требований
python3 SCRIPT mark RUN comparison start
python3 SCRIPT exec RUN --label unit-tests --basis 'AC: обязательный прогон связанных тестов' --cwd REPO -- npm test
python3 SCRIPT mark RUN comparison end
python3 SCRIPT mark RUN report start
# Сначала runner.py check RUN
python3 REPORT RUN/_meta/report.json --parts RUN/_meta/parts/manifest.json
python3 SCRIPT mark RUN report end
python3 SCRIPT summary RUN
```

exec запускает команду без shell, возвращает её exit code, сохраняет начало/конец и длительность; stdout/stderr остаются в вызывающей среде. Ограничения доступа и согласования среды действуют как обычно. Обёртка сама не выбирает тесты, не распараллеливает их и не устанавливает таймаут. При принудительном завершении может остаться только событие начала — это незавершённое измерение, не успех. Не передавайте секреты в аргументах команды или основании.

События хранятся отдельными файлами _meta/timing/*.json. Сборка отчёта пишет report_generated (время, размер JSON и файлов parts) либо report_failed. Количество событий показывает число попыток. Журнал не измеряет работу до prepare, скрытое рассуждение или токены. Метки фаз ставит агент, поэтому это приблизительные границы. Размер parts включает все JSON в каталоге, даже не включённые в manifest; это размер файлов, не объём токенов модели.

При исправлении меняйте конкретную запись и заново запускайте REPORT с --parts; Markdown и итоговый JSON формируются программно. Старый вызов без --parts поддерживается для прежних отчётов.
