# OpenSpec Spec Auditor — установка и запуск субагента

## Установка

Скопируйте agents/openspec-spec-auditor.md в `.gigacode/agents/`, а каталог agents/openspec-spec-auditor/ — в `.gigacode/agents/openspec-spec-auditor/`. В служебном каталоге обязательны INSTALL.md, report.schema.json, scripts/runner.py и scripts/report.py. Python 3 и Git должны быть доступны.

Обновляйте этот комплект согласованно, сохраняя резервную копию вне каталога агентов. Не заменяйте весь каталог agents и не затрагивайте другие инструменты. Начните новую сессию после установки. Корневой INSTALL.md пакета и устанавливаемый INSTALL.md содержат одинаковые инструкции.

В применимых проектных инструкциях закрепите: перед вызовом openspec-spec-auditor основной агент читает `.gigacode/agents/openspec-spec-auditor/INSTALL.md` и готовит задание по нему, не читая предварительно документы change для пересказа аудитору. Сам аудитор также обязан прочитать этот файл.

Пример задания:

> Вызови openspec-spec-auditor для полного change /absolute/store/openspec/changes/example, только статическое ревью. Сервис api: /absolute/repo/api; база: <SHA до реализации>. Результаты: /absolute/store/reviews/example.

## Перед выполнением

Координатор читает этот INSTALL.md до подготовки задания аудитору; аудитор читает установленный INSTALL.md до исследования проекта и вызова prepare. Если файл недоступен, прогон не начинается до восстановления комплектности установки. Эти инструкции описывают запуск, но не дают разрешения автоматически переустанавливать пакет или менять настройки проекта.

## Параметры запуска

Получите два независимых выбора: review_mode (`full_change`, `completed_subtasks`, `selected_subtasks`) и checks_mode (`static_only`, `run_required`). Если выбор явно задан пользователем, не спрашивайте повторно. Иначе уточните недостающие параметры и дождитесь ответа. Значений по умолчанию нет.

Передайте абсолютные change_path и service_paths, базы сервисов, известные ревизии, ID выбранных сабтасков, ограничения инструментов и write_access=confirmed/unknown с основанием. Не передавайте тексты требований текущего change, названия/описания сабтасков и прежние находки. Для completed_subtasks фактический список устанавливается после freeze. Это параметры задания; review_mode, checks_mode и results_root не являются CLI-флагами runner.py.

## Расположение результатов

planning-root — корень проекта, содержащий openspec/, определяется из `<planning-root>/openspec/changes/<change-id>`. Он может отличаться от корней сервисов.

```text
<planning-root>/reviews/<change-id>/<run-id>/
  observations.md
  report.md
  review-details.md
  _meta/
    inputs.json
    freshness.json
    report.json
    publication.json
```

runner.py prepare создаёт каталог прогона. `review_root` в inputs.json означает `<planning-root>/reviews`, а `results_root` в задании — `<planning-root>/reviews/<change-id>`. Используйте возвращённый prepare полный путь run. Не переносите его внутрь change. Весь `<planning-root>/reviews/` зарезервирован для аудитов и исключается из снимка кода; реализацию там хранить нельзя. Предыдущие прогоны сохраняются на месте.

До длительного анализа установите право записи в этот каталог. При отказе сообщите путь, операцию и причину. Смена cwd, успешная запись другим инструментом или копирование из временного каталога не доказывают разрешения. Альтернативный способ допустим только при установленном разрешении на операцию и конечный путь.

## Контекст и порядок чтения

Не повышайте reading_order до verified на основании собственного свидетельства без проверяемых внешних данных. Если среда не предоставляет достаточных свидетельств чистоты стартового контекста и соблюдения ограничений до freeze, unknown — допустимый результат; создание дополнительного файла или хеша не устраняет этот пробел. При установленном попадании запрещённых материалов до freeze используйте violated.

Для чистого старта используйте свежий контекст без требований текущего change, истории его реализации и прошлых аудитов. Само создание субагента или активация скилла не доказывает чистоту контекста.

1. До freeze исследуйте код; общие проектные правила, базовые спецификации и архитектурные материалы разрешены. Документы текущего change, копии/пересказы его требований и прежние аудиты запрещены. Не получайте их через поиск, Git или внешние инструменты. Хеширование скриптом без вывода содержимого допустимо.
2. Запишите observations.md и выполните runner.py freeze <run>. prepare и freeze выполняет аудитор. При ошибке freeze не переходите к требованиям.
3. После успешного freeze прочитайте change и выполните сверку в том же контексте. Не переписывайте зафиксированные OBS выводами из требований. Новые факты отражайте в coverage и доказательствах находок.

Прошлые аудиты запрещены и при сверке: исключайте `<planning-root>/reviews/` и прежний `<change>/reviews/` из поиска. Текущий run разрешён для собственных артефактов. Отдельно запрошенное сравнение прошлых прогонов выполняется после фиксации текущего результата.

reading_order.status: `violated` при установленном попадании запрещённых материалов до freeze; `unknown` при отсутствии установленной утечки и технического подтверждения независимости; `verified` только при внешних свидетельствах чистого контекста и проверенных условий изоляции до freeze. Основание сохраняется в reading_order.basis. Наличие файла на диске или его хеша не доказывает чтение. Временные метки, самоотчёт и успешный freeze не доказывают независимость. Пакет задаёт правила чтения, но не создаёт файловую песочницу.

## Проверки и публикация

После prepare используйте runner.py summary <run> для метаданных без содержимого требований. summary не заменяет runner.py check <run>.

static_only запрещает запуск тестов, lint, типов, сборки и диагностического кода проекта; штатные скрипты ревью выполняются. В run_required выполняйте необходимые проверки с конкретным основанием; достаточный запуск на неизменном снимке не повторяйте без нового основания. Чтение теста не подтверждает его успешное выполнение.

Запишите один _meta/report.json по установленной report.schema.json. Покрытие содержит отдельные обязательные условия и все OBS; reference_map/ref_id сокращают повторяющиеся ссылки, но не заменяют проверку полноты. После freeze для стандартных заголовков доступен report.py --list-references с повторяемым --reference-spec. При публикации передайте тот же набор файлов. Ссылки разрешаются относительно каталога отчёта, а не change.

Выполните check и report.py <run>/_meta/report.json. Скрипт публикует report.md и review-details.md. В основном отчёте — находки и решения, в приложении — покрытие и сведения проверки. Вердикт blocked_high_severity означает наличие high-находок; отсутствие high само по себе не доказывает полноту ревью или готовность к выпуску.

Для разбора прогона сохраните весь run и штатную трассу среды от задания до финального ответа, включая вызовы инструментов. Аудитор не создаёт отдельные журналы фаз. Укажите режимы, доступную модель и сведения о стартовом контексте.
