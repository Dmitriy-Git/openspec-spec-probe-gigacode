# openspec-spec-probe — один субагент

Редакция пакета 8.3; схема отчёта 8.0 с дополнительным вердиктом blocked_high_severity.

Скопируйте содержимое agents/ в .gigacode/agents/ вашего проекта, объединив каталоги. Файл openspec-spec-probe.md должен находиться непосредственно в agents/, а одноимённая папка со служебными файлами — рядом с ним. Не заменяйте целиком agents/: там могут быть другие субагенты. При обновлении удалите прежний .gigacode/agents/openspec-spec-probe-reverse.md, чтобы GigaCode не регистрировал второй агент. Другие агенты не затрагивайте. Проверьте /agents manage; при необходимости начните новую сессию.

После apply и ручных правок:

> Вызови openspec-spec-probe для change `my-change`. Задача: <Jira>; контекст: <Confluence>. Проверь текущую реализацию, включая незакоммиченные правки. Передай только пути, ревизии и ограничения. Открывай требования и обсуждения после freeze. Исключи предыдущие отчёты из контекста и поиска.

Передайте путь к исходному change. Агент фиксирует наблюдения по итоговому коду, сверяет их с требованиями и предлагает правки спецификации. При наличии ссылок на обсуждение и ревизий до и после ревью передайте их вместе с задачей.

Каждый запуск создаёт отдельный каталог внутри переданного change:

```text
openspec/changes/<change-id>/reviews/<run-id>/
  observations.md
  report.md
  review-details.md
  _meta/
    inputs.json
    freshness.json
    report.json
    publication.json
```

Читайте report.md для принятия решений и observations.md для проверки фактов о коде. В inputs.json сохраняются версии входов и SHA-256 зафиксированных наблюдений. Каталог reviews/ исключён из состава исходных требований. Для просмотра примера откройте examples/report.md.

Структура после установки:

```text
.gigacode/agents/
  openspec-spec-probe.md
  openspec-spec-probe/
    report.schema.json
    scripts/
      runner.py
      report.py
```

Минимальный комплект:

```text
INSTALL.md
agents/openspec-spec-probe.md
agents/openspec-spec-probe/report.schema.json
agents/openspec-spec-probe/scripts/runner.py
agents/openspec-spec-probe/scripts/report.py
```

Python 3, без внешних зависимостей. runner.py фиксирует входы и проверяет свежесть; report.py проверяет отчёт и создаёт Markdown. Инструкции обеих фаз находятся в единственном файле агента.

Внутренние команды (аргументы заполняет агент):

```sh
python3 .gigacode/agents/openspec-spec-probe/scripts/runner.py prepare /path/to/store/openspec/changes/my-change --service api=/path/to/src/api --base api=<base-commit> --source /path/to/task-export.md --rule /path/to/src/api/.gigacode/rules.md
# После записи observations.md и до чтения change:
python3 .gigacode/agents/openspec-spec-probe/scripts/runner.py freeze /path/to/run
# После сопоставления:
python3 .gigacode/agents/openspec-spec-probe/scripts/runner.py check /path/to/run
python3 .gigacode/agents/openspec-spec-probe/scripts/report.py /path/to/run/_meta/report.json
```

Для исторической мастер-спеки: --baseline-ref <commit-в-store>. Старый .spec-probe.json с adapter не используется. Старые отчёты не удаляются; отчёты прежних схем (включая 7.0) сохраняются для чтения; новые прогоны используют схему 8.0. Обновляйте инструкцию, схему и оба скрипта вместе.

Тесты вне пакета: `python3 -B -m unittest discover -s development/openspec-spec-probe-v4 -v` из корня исходного проекта.

Передавайте --rule отдельно для каждого прочитанного файла правил store и сервисов. Freeze обнаруживает последующие изменения наблюдений. Порядок чтения в общем контексте проверяйте по истории сессии.

## Изменения редакции 8.1

Усилены проверка ветвей поведения, основания keep/patch/ask/verify, согласованность spec/design/tasks и полнота предлагаемых правок. Процессные ограничения отделены от находок; наличие теста не считается успешным прогоном. Изменение исходного change остаётся вне задачи агента.

Отчёт показывает разбивку находок по причинам и полный нумерованный реестр вопросов, включая ask из находок. Один реестр используется для списка и счётчика; совпадающие по тексту вопросы после нормализации пробелов объединяются. Семантически похожие вопросы автоматически не объединяются. Валидатор отклоняет пустые доказательства и повторные ссылки. Проверка смысла доказательств и полноты правки остаётся обязанностью агента.

prepare принимает необязательный `--model <идентификатор>`; по умолчанию `unknown`. Значение передаётся вызывающей стороной и не проверяется автоматически. inputs.json дополнен временем подготовки и freeze, версией Python и хешами инструкции, схемы и скриптов. check проверяет также неизменность этих инструментов. publication.json содержит время последней генерации отчёта и хеши JSON/Markdown. Интервал prepare → публикация не является полной длительностью вызова агента. Для полного времени используйте журнал запуска.

Хеши позволяют сравнить и проверить состояние файлов, но не восстановить его: runner не копирует исходники. Для воспроизводимого пилота сохраняйте рабочий снимок отдельно, особенно при незакоммиченных изменениях. Внешний источник без экспорта с URL и версией остаётся ограничением воспроизводимости.

Схема 8.0 сохранена: старые отчёты остаются читаемыми; новые поля добавлены только в служебные метаданные. Обновляйте файл агента и оба скрипта вместе до нового прогона. Старые каталоги пакетов в исходном проекте не являются текущей версией для установки.

## Изменения редакции 8.2

Важность показывается цветными маркерами с текстом: 🔴 Высокая, 🟡 Средняя, 🟢 Низкая. Маркеры работают в Markdown без зависимости от поддержки HTML/CSS. Любая high-находка блокирует прохождение ревью: blocked_high_severity с перечнем ID. Неполнота проверки при этом остаётся видимой в проверках и ограничениях. Отсутствие high не отменяет остальные условия проверки.

Ноль находок признан нормальным результатом. Агенту запрещены квота замечаний, домысливание требований и повышение важности без обоснования последствий. Это правило рассуждения, а не программная гарантия истинности находок.

Обновите также report.schema.json: старый валидатор не знает нового вердикта. Старые отчёты читаются новым валидатором, итог при повторной генерации пересчитывается по новым правилам.

Уточнение итога: medium/low и вопросы владельцу допустимы. При завершённой проверке без high и проваленных тестов итог — passed_with_remarks («Ревью пройдено с замечаниями»). Пустой список не является целью агента. Схема дополнена этим вердиктом; обновляйте её вместе со скриптом.

## Представление отчёта в редакции 8.3

Основной report.md содержит итог, находки по важности, решения, вопросы и существенные ограничения. При более чем трёх находках добавляется указатель. Область проверки, проверки, покрытие и порядок чтения перенесены в review-details.md, доступный по ссылке из основного отчёта. publication.json фиксирует хеш обоих Markdown-файлов.

Находка начинается с последствия и решения; затем показаны требование и реализация. Необязательное поле sources в схеме позволяет отдельно указать путь, строки/раздел, язык и точный листинг до 15 строк. Дословные дубли доказательств и повторные ссылки внутри сопоставления/доказательств не выводятся повторно; дополнительные пояснения сохраняются. Старые текстовые поля поддерживаются; для сложных путей (в том числе с пробелами) используйте sources. Скрипт не читает указанные исходники и не подтверждает точность листинга: это обязанность агента.

Обновите инструкцию, report.schema.json и оба скрипта вместе. Пример нового вида — examples/report.md и examples/review-details.md. Порядок чтения сохраняется для аудита, но не занимает место в основном документе.
