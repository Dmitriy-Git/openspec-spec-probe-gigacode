# OpenSpec Spec Auditor: скилл для GigaCode CLI

Основа — openspec-spec-auditor 8.3-fast.9. Исходный пакет субагента не изменён.

## Установка

Скопируйте каталог `skills/openspec-spec-auditor` целиком в `.gigacode/skills/` целевого проекта либо в `~/.gigacode/skills/` для персональной установки. Не заменяйте весь каталог skills. При обновлении сохраните прежнюю версию отдельно и замените только этот скилл. Перезапустите GigaCode CLI.

В установленном каталоге нужны четыре файла: SKILL.md, report.schema.json, scripts/runner.py, scripts/report.py. Python 3 и Git должны быть доступны. Остальные файлы пакета нужны для проверки и сопровождения, устанавливать их не требуется.

Скилл доступен автоматически по описанию и явно через `/skills openspec-spec-auditor`. Пример задания:

> Используй скилл openspec-spec-auditor. Проверь весь change /absolute/store/openspec/changes/example, только статическое ревью. Сервис api: /absolute/repo/api; база: <SHA до реализации>. Результаты: /absolute/store/openspec/changes/example/reviews.

Другие варианты: «проверь выполненные сабтаски» или «проверь сабтаски ST-1 и ST-3», с путём subtasks.md. Для запуска необходимых проверок явно укажите это вместо статического режима. Недостающие режимы скилл уточняет; значений по умолчанию нет. Пути, ревизии и права записи должны соответствовать реальной среде.

## Сохранение поведения

Весь протокол исходного агента перенесён в SKILL.md без сокращения аналитических правил. После пилота усилены проверка стартового контекста, маршрут анализа по коду, контракт OBS, готовность к freeze и доказательство порядка чтения. Сохранены выбор области и проверок, проход по коду до freeze, покрытие условий, доказательность, решения patch/ask/keep/verify, проверка свежести, формат результатов и вычисление вердикта. Скилл записывает только материалы ревью в `<change>/reviews/<run-id>/`.

report.py и report.schema.json идентичны исходным. В runner.py хешируется SKILL.md вместо соседнего файла инструкции субагента; добавлена ранняя проверка, что каждый --source является существующим файлом, до создания каталога прогона. Контроль изменения инструментария остаётся действующим. Поля model и approvalMode субагента не перенесены в metadata скилла: используются модель и разрешения текущего агента. Обязанности координатора по параметрам запуска и уточнениям выполняет текущий агент. Полная карта замен находится в conversion-map.json.

Скилл не обеспечивает изоляцию контекста субагента. Для независимого первого прохода запускайте его в новой сессии, передавая только параметры, пути, ID, ревизии и ограничения. Если требования или предыдущие отчёты уже видны, протокол требует reading_order.status=violated; при непроверяемой истории — unknown. Одинаковое поведение модели в реальном GigaCode не гарантируется локальными тестами: необходим пилотный прогон в целевой среде. При сохранении установленного субагента в запросе явно указывайте, что нужен скилл.

## Проверки

Из корня этого пакета:

```sh
python3 -B -m unittest discover -s tests -v
```

examples/ содержит исходные образцы отчётов, evaluation.md — сценарии содержательной оценки исходного аудитора, применимые к скиллу. Тесты используют временные Git-репозитории и не запускают проверки рабочего проекта.

Правила формата и установки сверены с [официальной документацией GigaCode CLI](https://gitverse.ru/docs/ai/ai-assistant-gigacode/gigacode-cli/skills) 11 ноября 2026 года. Для расширений IDE следует отдельно проверить поддержку навыков и путь установки в конкретной версии.

## Ранняя активация

Добавьте следующий блок в применимый проектный GIGACODE.md целевого проекта (этот пакет сам не меняет проектные инструкции):

> При запросе аудита spec-auditor сначала загрузи скилл openspec-spec-auditor. До его этапа freeze не вызывай команды, раскрывающие содержание change, включая openspec show; не собирай предварительное резюме требований. Для запуска передавай только пути, ревизии, режимы, ID и ограничения. Не выбирай область кода через предварительное чтение требований. Если требования уже видны, сохрани reading_order=violated; не представляй активацию скилла как очистку контекста.

Правило должно действовать до активации скилла: один SKILL.md не может предотвратить предварительные действия вызывающего агента. Для независимого первого прохода нужна новая сессия без требований и прошлых отчётов; обязательный дополнительный субагент не вводится.

Для оценки следующих пилотов сравнивайте подтверждённые существенные находки, пропуски, режим проверок и полное время от запроса до ответа. Интервал prepare → публикация указывайте отдельно; он не включает подготовку. Прогоны с чистым и загрязнённым контекстом оценивайте раздельно. Не создавайте для этого дополнительные журналы во время обычного ревью.
