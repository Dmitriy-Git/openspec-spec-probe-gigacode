# Парный пилот OpenSpec Verify и Probe — редакция 8.1

Выберите два завершённых change: один типичный, второй с ручными правками после apply или несколькими сервисами. Запишите путь change, SHA базы и HEAD каждого сервиса, ревизию основной спеки до sync и версии доступных экспортов требований. Используйте одинаковые снимки рабочих деревьев, включая новые файлы, одинаковую модель и доступ к тестам. Откройте отдельную чистую сессию для каждой команды. Не передавайте второму участнику результаты первого. Если store общий, исключите reviews/ из чтения в обоих проходах.

### Команды в GigaCode

1. В чистой сессии GigaCode приложите [официальный скилл Verify](../openspec-verify-change.md) и отправьте «Выполни инструкции из приложенного Markdown для change <change-id>. Верни отчёт в чат». Если доступна команда `/opsx:verify <change-id>`, можно вызвать её напрямую. В контексте сессии заранее укажите пути store и сервисов, базы и источники. Попросите проверить текущие рабочие правки и исключить reviews/. Сохраните ответ отдельно.
2. В новой сессии отправьте: «Вызови openspec-spec-probe для <путь-change>. Сервисы и базы: <имя, путь, SHA>. Основная спека до sync: <ревизия>. Требования: <экспорты>. Проверь текущее рабочее дерево. Передай субагенту пути и ревизии, исключи содержимое change и предыдущих отчётов из стартового контекста». Сохраните report.md и observations.md.

### Карточка результата

| Факт, условие и место | Verify / Probe / оба | Достоверность по материалам | Доказательство или пробел |
|---|---|---|---|
| | | высокая / средняя / низкая | |

Считайте заявленные находки каждого инструмента и уникальные после объединения дублей по поведению и условию. Отдельно покажите совпадения, находки только одного инструмента и распределение уникальных находок по достоверности. Вопросы, незакрытые чекбоксы и невыполненные проверки считайте отдельно от содержательных расхождений. Строки покрытия одного факта не увеличивают число находок.

Достоверность оцените при сравнении отчётов по одной шкале для обоих инструментов. Высокая — конкретное требование и наблюдаемый эффект подкреплены проверяемыми ссылками или воспроизводимой проверкой. Средняя — есть предметные доказательства, но остаётся непроверенное звено или альтернативная трактовка. Низкая — основание косвенное, отсутствует или противоречит другим данным. Для правки оцените также источник намерения; при разных оценках факта и предлагаемой правки объясните разницу. Это предварительная оценка по доказательствам. Метки принятия владельцем не требуются.

Запишите модель, длительность и снимок входов. При повторе того же change отдельно покажите сохранённые, новые и пересмотренные находки. Исключите предыдущие отчёты из стартового контекста и области поиска. Для оценки эффекта порядка чтения используйте только свежие прогоны с verified и проверяемой историей. При violated или unknown находки остаются в содержательном сравнении. Повтор того же change учитывайте отдельно от второго независимого примера.

### Уточнения после пилота

До начала пары убедитесь, что apply завершён и оба участника видят одну реализацию. При незакоммиченных правках одного HEAD недостаточно: сравните хеши рабочих файлов, включая новые, и сохраните снимок для воспроизведения. Фиксируйте модель каждого участника отдельно; unknown не подтверждает равенство моделей. Полную длительность берите из журналов вызовов, не из mtime файлов и не из интервала prepare → публикация.

В карточке добавьте тип результата: дефект реализации, пробел/противоречие требований, риск, рекомендация, процессное состояние или ограничение проверки. Содержательные расхождения считайте отдельно от остальных типов. Вопрос ask — действие по соответствующей находке, а не ещё одна находка. Сходная тема не означает дубль: сопоставляйте условие и результат. Для каждого исходного ID сохраните соответствие итоговому ID либо объяснение исключения; находки не должны теряться при дедупликации.

Для каждого patch оцените отдельно обоснованность намерения и полноту согласования связанных spec/design/tasks/AC. Проверяйте ошибочные ветви, ранние выходы и жизненный цикл только там, где они применимы к требованию. Не путайте существование теста с его успешным выполнением.

Повтор после apply не доказывает, что прежние замечания исправлены благодаря ревью: нужна история изменений. Один парный прогон также не выделяет эффект порядка чтения. Для проверки этого эффекта нужны одинаковые задания и входы с изменённым только порядком чтения.
