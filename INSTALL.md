# OpenSpec Spec Auditor — аудитор спецификации

Основа: Probe 8.3; схема 8.0. Оригинальный Probe не изменён. Структура результатов возвращена к обычному Probe:

```text
<change>/reviews/<run-id>/
  observations.md
  report.md
  review-details.md
  _meta/
    inputs.json
    freshness.json
    report.json
    publication.json
```

Один report.json, без parts, manifest, реестра доказательств и событий времени. Сохранены выбор области ревью, пакетное чтение, правила доказательности и обоснование повторных тестов. Расширения схемы: необязательный in_scope для наблюдений вне выбранных сабтасков и reference_map/ref_id для повторяющихся ссылок покрытия. Оно не создаёт дополнительных файлов.

## Установка и обновление

При переходе с прежнего имени `openspec-spec-probe-fast` перенесите его файл `.md` и одноимённый служебный каталог из `.gigacode/agents/` в резервную папку. Установите пакет под новым именем `openspec-spec-auditor` и обновите вызовы в проектных инструкциях. Суффикс `fast` в имени агента больше не используется; обозначения `8.3-fast.*` ниже сохранены как история редакций.

Скопируйте agents/openspec-spec-auditor.md и файлы из agents/openspec-spec-auditor/ в соответствующие места .gigacode/agents/. Обновите вместе инструкцию, report.schema.json, scripts/runner.py и scripts/report.py. Не заменяйте весь каталог agents и не затрагивайте обычный Probe.

Для чистого обновления перенесите прежний установленный каталог openspec-spec-auditor/ целиком в резервную папку вне .gigacode/agents, затем установите свежий каталог из этого пакета. Это исключит оставшиеся инструкции, скрипты и кэш старой версии. Соседний файл openspec-spec-auditor.md тоже замените. Остальных агентов не затрагивайте. Предыдущие каталоги reviews сохраняйте: новая версия их не читает и не преобразует.

В установленном служебном каталоге достаточно трёх файлов:

```text
report.schema.json
scripts/runner.py
scripts/report.py
```

Начните новую сессию, чтобы старые инструкции о parts и тайминге не остались в контексте. Если ранее добавляли проектную заметку о fast.3, обновите её: новый прогон использует один report.json. tests/ не нужно устанавливать в каталог агентов.

## Выбор области основным агентом

До вызова openspec-spec-auditor определите область из явного запроса пользователя. Не спрашивайте повторно при однозначном запросе. Если пользователь просит только «запусти openspec-spec-auditor», уточните: «Проверить весь change или выполненные/конкретные сабтаски из subtasks.md?» Наличие subtasks.md само по себе не определяет режим.

Передайте субагенту один из вариантов:
- `review_mode: full_change` — полный change;
- `review_mode: completed_subtasks`, `subtasks_path: <путь>` — выполненные сабтаски; агент установит список после freeze;
- `review_mode: selected_subtasks`, `subtasks_path: <путь>`, `subtask_ids: [<ID>, <ID>]` — конкретные сабтаски.

Это параметры задания в тексте вызова, не новые флаги runner.py. Передавайте только режим, ID, пути, ревизии и ограничения; не передавайте содержание требований или старые отчёты. Если агент возвращает вопрос о неоднозначной выборке, передайте его пользователю и верните ответ субагенту. Не выбирайте за пользователя.

Примеры пользовательских запросов:

> Вызови openspec-spec-auditor для полного change <путь-change>.

> Вызови openspec-spec-auditor для выполненных сабтасков из <путь-change>/subtasks.md.

> Вызови openspec-spec-auditor для сабтасков <ID-1> и <ID-2> из <путь-change>/subtasks.md.


После прогона для анализа достаточно передать report.md, review-details.md и при необходимости _meta/report.json, observations.md и журнал вызова. Ускорение не гарантируется: эта редакция устраняет накладные расходы формата.

## Проверки в fast.5

В режиме run_required lint, типы, тесты и необходимая сборка выполняются единым финальным этапом после сопоставления и до публикации. Один достаточный запуск на вид проверки; повтор — только с новым основанием. Ранний целевой запуск разрешён, если нужен для анализа, и без изменения входов не дублируется в конце. Обязательные правила проекта сохраняются; full_change не означает автоматический запуск всех проверок проекта. Каталог _meta остаётся из четырёх штатных файлов.

## Компактные данные fast.6

Обновите вместе файл агента, report.schema.json и scripts/report.py. Повторяющиеся ссылки coverage хранятся один раз в reference_map того же report.json. Генератор раскрывает их в приложении. Старый формат с ref поддерживается. Основной отчёт, поля находок и листинги не изменены; пояснения успешных проверок пишутся кратко без потери доказательств. Дополнительных файлов нет.

## Запуск fast.8

Основной агент до запуска получает два выбора: область ревью и запуск проверок. Если пользователь уже указал выбор, не спрашивайте о нём повторно. Иначе одним сообщением уточните недостающие параметры и дождитесь ответа:

1. Весь change, выполненные или конкретные сабтаски?
2. Только статическое ревью или запуск необходимых проверок?

Ни review_mode, ни checks_mode не имеют автоматического значения по умолчанию. Передайте ответы как full_change/completed_subtasks/selected_subtasks и static_only/run_required. Это параметры задания, не CLI-флаги. Передайте абсолютные пути change и сервисов, базы, ID выбранных сабтасков, results_root=<change>/reviews, подтверждение права записи и известные ограничения инструментов. Содержание требований и прежних отчётов не передавайте.

После prepare агент вызывает `python3 <полный-путь>/runner.py summary <run>`: получает пути, ревизии и список изменённых путей кода без карты хешей. Команда не меняет файлы и не проверяет свежесть; check остаётся обязательным. Полный inputs.json хранится для скриптов.

Для обновления fast.7 замените файл агента и scripts/runner.py. Остальные файлы пакета совместимы, структура отчёта не менялась. Передайте этот раздел основному агенту и начните новую сессию. Установка файла субагента сама по себе не обновляет инструкции основного агента.

Сравнение прошлых прогонов и анализ времени выполняются только по отдельному запросу после фиксации текущего ревью. Привязка результатов к выбранным сабтаскам сохраняется.

## Оптимизация fast.9 по замерам пилота

Обновите вместе файл агента и scripts/report.py; runner.py и схема совместимы с fast.8. Исправлена разметка имён с несколькими точками (`http.test.ts`, `eslint.config.js:96-105`) и абсолютных/относительных путей. Компактные основания coverage сохраняют факт, метод и источник, без повторения требования.

После freeze агент может получить карту стандартных заголовков без записи дополнительного файла:

```sh
python3 /absolute/path/report.py --list-references --reference-spec /absolute/change/specs/example/spec.md
```

В авторском JSON используются выданные ref_id, а reference_map не пишется моделью. Публикация с тем же набором файлов добавляет карту автоматически:

```sh
python3 /absolute/path/report.py /absolute/change/reviews/RUN/_meta/report.json --reference-spec /absolute/change/specs/example/spec.md
```

Для нескольких файлов повторяйте --reference-spec. Прямые ref остаются совместимы; нестандартные заголовки и задачи требуют явных ссылок. Индекс не заменяет чтение, выбор области и сверку покрытия. Новый флаг не запускает тесты проекта и не меняет вердикт.

До вызова передавайте известные base/head, абсолютные пути скриптов и подтверждённый способ записи в results_root. Не включайте неизменённые сервисы без связи с проверяемым поведением; связанные зависимости исключать ради скорости нельзя. Запрет записи решается разрешениями среды, а не сменой инструмента. Пакет не изменяет настройки среды автоматически.

Повторный прогон на том же коде не пропускается автоматически: режим, область, правила, требования, инструменты и внешние условия тоже влияют на результат. Ускорение fast.9 ещё нужно измерить на реальном прогоне; размеры JSON и время публикации из скриншотов не дают надёжного прогноза в минутах.
