# Адаптер выполнения v3

Runner реализован на Python 3 без зависимостей. Он готовит снимки, запускает три генерации, аудит каждого пакета, три reverse и compare, проверяет хеши и валидирует отчёт. Модель вызывает локальный адаптер через subprocess, без shell-интерполяции.

**Предел готовности:** готового проверенного адаптера GigaCode/sandbox в комплекте нет. В среде разработки GigaCode отсутствует. До настройки адаптера полный цикл не запускается. Frontmatter, отдельный cwd и заявление модели не обеспечивают изоляцию. Адаптер — доверенная часть системы; его evidence нельзя принимать от LLM. Интеграционный пилот обязателен.

## Однократная конфигурация

Координатор создаёт `.spec-probe.json` в корне рабочего проекта. Это внутренний файл, пользователь не обязан заполнять переменные каждого запуска.

```json
{
  "plan_root": "specs-repo",
  "services": {"api": "src/api", "web": "src/web"},
  "sources": [
    {"path": ".spec-probe-sources/task.txt", "url": "https://jira.example/browse/APP-1", "version": "updated timestamp"},
    {"path": ".spec-probe-sources/context.txt", "url": "https://wiki.example/page", "version": "12"}
  ],
  "adapter": ["/absolute/path/to/validated-runtime-adapter"]
}
```

plan_root/services можно не задавать для однозначной структуры store рядом с src/. Внешний зарегистрированный store разрешает координатор по штатным настройкам OpenSpec и сохраняет абсолютный plan_root. Поиск по соседним каталогам не заменяет приоритеты OpenSpec. sources — локальные зафиксированные экспорты; их получение выполняет координатор доступным коннектором. Не хранить токены в конфигурации.

## Протокол процесса

Для каждого этапа runner вызывает argv адаптера с дополнительными аргументами:

```
--stage generate|audit|reverse|compare --input ABS_DIR --output ABS_DIR --request ABS_JSON
```

Процесс завершается с ненулевым кодом при ошибке. Не возвращать успех после отказа модели/таймаута. Адаптер сам ограничивает время и ресурсы процесса. Каждый generate/reverse — новая сессия без истории родителя. Один запуск не зависит от результатов соседних проб. Последовательное выполнение трёх проб допустимо.

- **generate:** input содержит code, change, sources, baseline-specs. Получить независимую реализацию на копии; сохранить полный код всех сервисов в output/code, включая неизменённые файлы. Не оставлять симлинки. Записать версии runtime/модели, prompt digest, выполненные команды и результаты. Не менять оригиналы. OpenSpec apply использовать только после проверки интерфейса установленного CLI.
- **audit:** доверенный подготовитель видит package и исходный change из request. Проверяет источники, код, diff, базовые спеки, тесты, комментарии на копии/пересказы change; удаляет утечки, отражает исключения в output. Нельзя удалять законные внешние требования лишь за совпадение с change. После изменения кода согласовать diff. Вернуть audit.json: `approved: true`, `package_hashes: {relative_path: sha256}`, перечень исключений и основания. Нерешённая утечка — approved=false. Аудит не выполняется в контексте reverse.
- **reverse:** смонтировать только проверенный package read-only и пустой output read-write в контейнер/эквивалентный sandbox. Не передавать manifest всего запуска, host paths, audit, историю, change, домашний каталог, конфигурацию с секретами, другие реализации, git objects, MCP или web. Модельный transport может обслуживаться снаружи доверенным launcher; у инструментов reverse нет сети. Проверить отказ доступа к host/change/соседям/сети до запуска. Если ограничение не обеспечено — отказ, а не best effort. Восстановить артефакты и сохранить их в output. Для утверждений отмечать `source_requirement` с источником или `code_observation` с file:line/тестом; несовпадения сохранять.
- **compare:** видит весь run и рабочий контракт. Проверяет свежесть meta, покрытие требований в change отдельно от поведения, тесты, риски и ограничения. Записывает output/report.json по существующей схеме 2.0. Не выдумывает implementation SHA для снимков без коммитов: использует хеши и явно обозначает unknown там, где требуется SHA. Полные метаданные снимков — в manifest. Отсутствующие проверки ограничивают вердикт.

После завершения reverse **launcher**, вне writable пространства модели, создаёт output/isolation.json:

```json
{
  "enforced_by": "launcher",
  "mechanism": "actual configured sandbox mechanism and version",
  "probe_log": "path or embedded results of actual negative access tests",
  "host_files_denied": true,
  "change_denied": true,
  "siblings_denied": true,
  "network_denied": true,
  "fresh_context": true
}
```

Runner проверяет наличие полей и хеши; достоверность свидетельства обеспечивается доверенным адаптером, не JSON-флагами. Он не является реализацией sandbox. Тестовый mock не доказывает безопасность реального runtime.

## Выходы и ошибки

`.spec-probe/<unique-run-id>/manifest.json` фиксирует исходные хеши, источники, завершённые этапы, статус и ошибку. Итог: `result/report.json`, `result/report.md`. Входы фиксируются до трёх генераций. Повторный вызов создаёт свежий run; старый не перезаписывается. Автоматического resume нет. Частичные результаты сохраняются для диагностики. Незавершённый запуск не получает вердикт spec_ready.
